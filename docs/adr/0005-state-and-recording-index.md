# 0005. Camera state over MQTT, and the recording index

## Status
Accepted (2026-10-24).

## Context
Two facts about each camera must be visible to the right tenant only: whether it is connected (and whether it is recording), and which recorded segments exist. MQTT 5.0 gives a keep-alive timer, a Will message and retained messages ([MQTT 5.0, OASIS](https://docs.oasis-open.org/mqtt/mqtt/v5.0/mqtt-v5.0.html)): if the broker receives nothing from a client for one and a half times the Keep Alive, it closes the connection and sends the Will; a normal DISCONNECT discards the Will. MediaMTX records fragmented MP4 segments and can run a command when one is complete, and its Control API lists what is on disk ([record](https://mediamtx.org/docs/features/record); `/v3/recordings/get` in MediaMTX 1.21.2 `internal/api/api.go`, seen in `docs/validation/poc.md`). The Mosquitto dynamic security plugin controls who may publish and subscribe where, with `%c` and `%u` in an ACL topic replaced by the client id and user name ([dynamic security](https://mosquitto.org/documentation/dynamic-security/)).

## Decision

### State
- MQTT 5.0, Keep Alive **60 seconds**: the default of the MQTT client library the camera uses (paho-mqtt 2.1.0, `connect(..., keepalive: int = 60, ...)`; its documentation of the argument: "Maximum period in seconds between communications with the broker."). The broker gives up on a client after one and a half times that, 90 seconds. The camera, the API's intake and its administration client use 60. Until 2026-10-26 the value was 10 seconds, with no model; the first version's integration test `tests/integration/test_05_liveness.py` now checks 60 x 1.5 = 90 seconds (plus 5 seconds of slack), see `docs/validation/acceptance.md`. Topic `cameras/<camera uuid>/state`. Client id = user name = the camera's UUID. The tenant is never in the topic; the API looks it up in the database.
- The topic has `<camera uuid>` as a whole level because `%c` only works when it is the only text in its level. So **one** role covers all cameras: `publishClientSend` on `cameras/%c/state` and nothing else (the default for subscribe is deny, so a camera cannot subscribe to anything). The intake user has one role with `subscribePattern` on `cameras/+/state` and no publish rule. The dynsec administrator is a third credential, used only by the API to create camera users. Proof 3 in `docs/validation/poc.md` shows that publishing to another camera's topic is refused with reason code `0x87` and that connecting with a different client id fails.
- When a camera connects it publishes `{"state":"online"}` retained. Its Will is `{"state":"offline","reason":"will"}` retained. On SIGTERM it publishes `{"state":"offline","reason":"normal"}` retained itself and then disconnects. Every 60 seconds it publishes `{"state":"online","fps":..,"bitrate":..}`: the interval at which Frigate publishes its camera and system stats over MQTT (`stats_interval`, default 60, Frigate 0.18.2 `frigate/config/mqtt.py`: "Interval in seconds for publishing system and camera stats to MQTT."; its topic `frigate/stats` carries the "Same data available at `/api/stats`", which has each camera's `camera_fps`). This message is the camera's figures, as Frigate's is, and not the sign that it is alive: that is the Keep Alive and the Will above (the API has no time-out on the last message), as Frigate's own `frigate/available` is "online" on connecting and "offline" by the Will. Until 2026-10-26 it was every 30 seconds, a value without a source; the load test (0010) was made then.
- **Shown state:** `online` and the MediaMTX path is ready (Control API `/v3/paths/list`) = *recording*; `online` and no path = *standby*; `offline` or never seen = *disconnected*.
- Detection time after a silent loss (for example a paused container) is Keep Alive x 1.5 = 90 seconds; after `docker kill` the broker sees the closed socket and sends the Will at once.
- Mosquitto uses its own configuration: no anonymous access, one listener inside the compose network, no HTTP API listener, the dynamic security plugin. `mosquitto_ctrl dynsec init` creates the plugin's file on the first start (it is run by the broker container's own start script, `infra/mosquitto/entrypoint.sh`, because `mosquitto_ctrl` exists only in that image; the administrator password is read from the file the init container wrote). Mosquitto 2.1 would otherwise generate a default file with a demo client that can read and write every topic). The API creates the roles, the intake user and the camera users when it starts, and again when a camera is registered; every command can be repeated.

### Recording index
- Segments are 60 seconds (`recordSegmentDuration`; MediaMTX's default is one hour). 60 seconds is the length of Moonfire NVR's recordings: its time design says it saves video streams "into roughly one-minute *recordings*" (`design/time.md`; Moonfire is GPL-3.0, the fact is cited, nothing copied). Segments are fMP4, path pattern `./recordings/%path/%Y-%m-%d_%H-%M-%S-%f`, deleted after one day (`recordDeleteAfter: 1d`, MediaMTX's default).
- After each segment MediaMTX runs `sh /segment-hook.sh`, which posts `path`, `file` and `duration` with a shared secret header to the API's internal door with BusyBox `wget`. (The start time is not passed; it is read from the file name. The name is in the local time zone of the MediaMTX process, which is UTC only because the container sets no TZ.) The command in `mediamtx.yml` is not run through a shell (MediaMTX 1.21.2 `internal/externalcmd/cmd_os_other.go` splits it into words and runs it directly; MediaMTX itself puts in the `$MTX_...` variables), so a script is used rather than `$(...)` in the setting.
- The API stores one row per segment, with the key (camera, start time) and `ON CONFLICT DO NOTHING`. The camera must exist and the tenant in the path must be its tenant.
- **Reconciliation** every 900 seconds: the default of ZoneMinder's audit daemon, which matches the database of recorded events with the files on disk and removes what is only in one of them (`ZM_AUDIT_CHECK_INTERVAL`, `scripts/ZoneMinder/lib/ZoneMinder/ConfigData.pm.in`: "The default check interval of 900 seconds (15 minutes) is fine for most systems"; ZoneMinder is GPL-2.0, the value is cited, nothing copied). Until 2026-10-26 it was every 60 seconds, a value without a source. The 90-second grace below is the author's design decision; no model was found for it (looked at: ZoneMinder's `ZM_AUDIT_MIN_AGE`, "Event files or db records that are younger than this setting will not be deleted", default 86400 s, which is longer than a recording is kept here (one day), so a lost segment would never be added; Frigate's recording maintainer, which skips a file that ffmpeg still has open and uses no time; Frigate's recording cleanup and MediaMTX's record and Control API documentation). For each camera the API asks `/v3/recordings/get/<path>`, which returns the start times of the segments on disk. It inserts the starts the index lacks (a lost hook call) and marks as deleted the rows MediaMTX no longer has (automatic deletion). Segments younger than 90 seconds are left to the hook because the open segment is listed before its hook fires. `/v3/recordings/get` does not return durations, so gap rows have no duration.
- **Why keep an index when MediaMTX can list recordings:** to search across tenants and cameras with SQL, to join recordings with other tables later, and to search across several MediaMTX instances later. MediaMTX's own `/list` joins consecutive segments into one span, so it is not used for matching.

## Consequences
- A camera that is paused for less than 90 seconds is not noticed; one paused longer shows as disconnected and returns to online by itself when it runs again.
- Retained `online` messages mean a new subscriber learns a camera's last state, but a broker restart forgets them (persistence is off, Mosquitto's default) until the cameras reconnect or publish their next state message (at most 60 seconds).
- The state needs two sources (MQTT and MediaMTX); if the Control API is unreachable every online camera shows as *standby*.
- The hook is best effort; reconciliation guarantees completeness within about 16.5 minutes (900 seconds plus the 90-second grace; about a minute and a half until 2026-10-26).
- Camera MQTT users created before the dynsec volume was lost cannot be recreated for cameras registered through the API (only the hash of their secret is stored); delete and register them again.
- `/v3/paths/list` is read without paging; with more than a page of cameras (the default page size is 100 items, MediaMTX 1.21.2 `internal/api/paginate.go`), the ready set would be incomplete. Fine for a demonstration.

## Alternatives not chosen
- **Matching against MediaMTX `/list`.** It merges consecutive segments, so single missing segments cannot be seen.
- **A topic with the tenant in it** (`<tenant>/<camera>/state`). `%c` cannot express "my camera inside my tenant" in one role.
- **Putting a queue between MQTT and the database.** Not needed before the load is measured.
